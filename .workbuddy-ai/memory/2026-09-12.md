### 值得记住的技术判断

1. **列表里没有 MIME**：S3 与 WebDAV 都把 `Content-Type` 留空，worker 只透传。要按 MIME 分派就得先下载一遍
   → 所以**只能按扩展名**分派。`svg` 有意归到"图片"（文件管理器就该显示成图）。
2. **`/d/*` 是要鉴权头的**，浏览器不给子资源带 `Authorization`，所以 `<img src="/d/...">` 永远不行
   → 一律 `fetchFileResponse()` 取字节转 object URL。**OpenList 的 `/d/*` 是公开的（只有 signCheck），这个项目有意不公开**。
3. **`URL.createObjectURL(await blob)` 是"整份文件进内存才显示"**，`preload="metadata"` 救不了（blob 到元素时已完整）。
   实测真实桶 51 MB 录音半分钟没出来 → `BLOB_SIZE_LIMIT = 16 MB`，超限给说明面板且**不取字节**。
   **用户明确说过这一步下载功能不可用**，所以超限不再退回下载。
4. **懒加载 Monaco 是双赢**：入口包 8,100,278 → 467,387 字节（−94%），Monaco 隔离进 7.6 MB 分块；
   同时让分派器可以在 Node 里 `renderToStaticMarkup`（测试的前提）。
5. **pnpm 会嵌套 React**：`@typefox/monaco-editor-react` 把 React 声明成普通依赖（不是 peer），
   于是在它下面装了 19.2.8（应用 19.2.1），dev server 的依赖预打包把这份内联进去 → 打开文本就 `Invalid hook call`。
   **生产构建是干净的**（Rollup 会去重），只有 dev 会中招。用 `resolve.dedupe: ["react","react-dom"]`。

### 两个真 bug（都不是这一步引入的）

- **Hono 裸 `*` 不是 param**：`app.on(..., "/d/*", ...)` 里 `c.req.param("*")` 是 `null`，路径塌成 `/`，
  **每次下载、以及 `/api/fs/link` 发出去的每个 URL 都 404 "Storage not found"**。必须具名：`/d/:name{.*}`。
  已反向验证过（改回旧写法 → 测试失败）。
- **markdown 渲染器递归时共用全局正则**：内层调用重置 `lastIndex`，外层从同一匹配重启 → 输出无限增长 →
  `RangeError: Invalid string length`。递归前先把匹配物化到 `new RegExp(source, "g")` 的副本上。

## 阶段八 8.5：目录缓存（`caches.default`）

### 做了什么

`src/worker/storage/cache.ts`：按**虚拟路径**做键的目录列表缓存，TTL 取 `cache_expiration`（默认 30 分钟），
`custom_cache_policies`（`pattern:minutes` 一行一条，doublestar glob）覆盖它，`refresh` 同时跳过读**并重写**条目。
`fsList` 改成走 `listDirectory`；所有写路径（mkdir / rename / remove / put / form / copy / move /
remove_empty_directory）按"**持有该条目的那个目录**"失效（不是条目自己）。
恢复了 0.2 移除的 `cache_expiration` / `custom_cache_policies`：registry 公共项重新声明（`noCache` 驱动不声明），
`normalizeStorageConfig` 把它收敛成非负整数（备份里的 `"30"` 要能读，读不出回落 30，负数夹到 0＝不缓存），
`registry.test.ts` 加"表单提供的缓存字段必须被 `storage/cache.ts` 真的读到"的守卫。
另外把 `parentOf` 补进 `worker/storage/types.ts`（前端 `lib/paths.ts` 早有同名函数，两边各一份，worker 不引前端代码）。

### 值得记住的几点

1. **缓存键必须是虚拟路径**：OpenList 的 `Key(storage, path)` 是 `GetFullPath(mount_path, path)`，也就是客户端请求的那个路径。
   若按适配器拿到的相对路径做键，挂载在 `/` 的 `/docs` 与挂载在 `/waynecos` 的 `/docs` 会**撞成同一条**、互相顶掉。
   已用 `envWith(["/", "/waynecos"])` 的集成测试钉死这一点。
2. **空列表要删条目，而不是只"不写"**：OpenList 对空结果走 `deleteDirectoryTree`。只不写的话，
   `refresh` 后发现目录已空时旧条目还在，接下来整个 TTL 都会把删掉的内容又端出来——比不缓存更糟。
3. **`caches.default` 不跨数据中心、无法枚举**，所以失效只在处理写请求的那个 DC 生效。
   因此前端**写之后的重载必须带 `refresh: true`**（新增 `FilesPage.reloadAfterWrite`，工具栏 Refresh 同样带），
   否则"上传成功但列表里没有"会是个真 bug。**TTL 才是陈旧度的真实上界，失效不是。**
4. **`/docs/**` 不匹配 `/docs` 本身**（shell 语义）。第一版单测断言写成匹配，是断言错不是代码错。
   glob 匹配的是**存储内相对路径且带前导斜杠**（`/docs/a`），与 OpenList 传给 `doublestar.Match` 的一致。
5. 接入点**只有 `fsList`**；`fsSearch` / `fsDirs` 仍直连适配器（它们一次走很多目录，把用户从没打开过的目录
   灌进边缘缓存不划算）。
6. `noCache` 分支今天三个驱动都没声明，**没有测试覆盖**，留着是为了下一个驱动。
7. `tsc -b` 的 `-b` 模式与 `vitest` 前台运行在沙箱里都会被 SIGTERM 杀掉（连空输出都没有）。

## 阶段八 8.6a：分片上传后端（S3 multipart）

### 做了什么

把 3.10 留下的 **501 骨架**换成真的实现。`StorageAdapter` 增加**可选**的
`multipartInit / multipartUploadPart / multipartComplete / multipartAbort`，`StorageCapability` 增加
`multipart`，只有 S3 驱动声明。新增 `src/worker/multipart.ts`（五个处理器 + KV 会话），
路由改成 `POST /init`、**`PUT /chunk`**、`POST /complete`、`POST /status`、`POST /abort`。

### 值得记住的几点

1. **3.10 的说法是虚的**：它写"新增分片上传骨架，仅 S3 驱动可用"，实际五个端点全部 `return failure(..., 501)`。
   所以 8.6 从来不只是前端接线——后端一直是空的。已在 TODOLIST 里更正 3.10 并拆成 8.6a / 8.6b。
2. **`PUT /chunk` 才对**：原骨架把它注册成 POST，上游 OpenList 是 `multipart.PUT("/chunk")`，语义上块也是
   "放上去的字节"。第一版测试按 PUT 写，直接 404 才发现的。
3. **S3 会把给它的分片按顺序拼起来，并且无论对错都返回成功**。少一块 = 文件静默变短。所以 `complete` 之前
   必须自己校验：分片号恰好是 1..n、总字节数等于 init 时声明的 size，否则 400。**这是唯一挡住静默截断的东西。**
4. **块号 0 基、分片号 1 基**，只在边界翻译一次。
5. **重传同一块是替换不是追加**（provider 按号索引分片，我们也按号索引），所以网络重试安全。
6. **KV 的 TTL 就是唯一的清理机制**：Worker 没有常驻内存也没有后台任务，被放弃的上传没人回收，
   只能等会话过期（provider 侧的分片会一直挂着）。另外会话是 read-modify-write，所以**块必须一个一个传**，
   并发会丢块号；KV 跨地域最终一致，同一 DC 内才即时可见——两条都写进模块注释了。真要强一致得上 Durable Objects。
7. 会话 id 由我们自己发（32 位 hex），**provider 的 UploadId 不下发**；id 会从客户端回来并直接变成 KV 键，
   所以先按形状校验再当键用。
8. 复用 `fsPut` 的写入检查（`canWrite` + `ObjMask.NoWrite` 查父目录），为此把 `checkWriteMask` 从 `fs.ts` 导出，
   否则分片上传会绕开 Meta ACL 和掩码。
9. 块大小低于 5 MiB 会被忽略并回落默认 8 MiB（S3 除最后一块外不接受更小的分片），返回值里带 `chunk_size`，
   **客户端必须照着返回的切**。

## 决定与理由（跨会话仍然成立的部分）

1. **上限取 100 MB，而且只有这一个数字站得住**。Cloudflare 按**账号套餐**限制请求体（Free/Pro 100 MB、
   Business 200 MB、Enterprise 自助最高 5 GB，见 Workers 平台 limits 文档）。超限请求在**边缘就被 413 挡掉，
   Worker 代码根本不运行**——所以服务端给不出更友好的提示，客户端也问不到自己是什么套餐。100 MB 是文档化的
   **下限**，Business/Enterprise 只是比理论必要值更早走分片，代价是几次额外往返。
2. **能力由 worker 下发**：`getDriverInfo()` 增加 `capabilities`（`Set` 过不了 `JSON.stringify`，排序求稳定）。
   前端 `chunkableMounts()` 用「存储的 driver」×「驱动的 capabilities」推出哪些挂载点能分片，用的是 worker
   解析时的**同一份注册表**，所以两边不可能走偏。
3. **`chunkable` 是三值的**：`null`＝还不知道，未知时**照分片试**（和 `unwritableHint` 同一个理由：猜"不能"
   会拒掉本来能成的上传；猜"能"只多一个请求，worker 会用清楚的话拒掉，且超限文件本来也没别的路）。
4. **分片大小不听前端**：用 `init` 返回的 `chunk_size`。5 MiB 下限和默认值都归服务端，前端再存一份就是会漂移的副本。
5. **只重试块**。块是唯一可安全重复的步骤（服务端按 part number **替换**而不是追加，这条 8.6a 已确认）。
   `init`/`complete` 不重试：第二次 init 会留下没人认领的会话，第二次 complete 会发现会话已被第一次删掉。
   单个 `PUT` 也重试（大 body 最容易撞断连，PUT 到路径幂等）。
6. **`api()` 现在抛 `ApiError`（带 `status`）**，`ApiError extends Error` 所以既有调用点一行不用改。
   `isRetryable`：`TypeError`（fetch 没到服务器）算可重试；429/5xx 可重试；400/401/403/404/413 不可重试
   （413 尤其不能重试——那会把整个 body 再发一遍）。非 `ApiError` 的自造错误（上限拒绝）也不可重试。
7. **abort 的边界分得很清**：`init` 失败**不** abort（会话根本没开），块失败或 `complete` 失败才 abort。
   理由还是那条——Worker 没有后台任务能回收被放弃的上传。
8. **上限提示只在会咬人的地方出现**：只有确定不能分片的存储才显示工具栏那句能力说明（`data-testid="ceiling-hint"`），
   **未知不提示**。对可能不存在的限制报警，会让人连真的警告一起无视。目录压根没存储时 `writeHint` 已经说了，不重复。
9. **进度要动**：分片文件自己报字节百分比（`UploadProgress.bytes`），否则"上传 2/5"几分钟不动，读起来像卡死。

## 已知取舍（记下来而不是悄悄留着）

- `multipartInit` **不发送 `Content-Type`**，所以走分片上传的对象会拿到 provider 的默认类型，而单请求 `PUT`
  会带上真实类型。预览侧 `withMime()` 按扩展名兜住了，所以没改——要改就是给 `multipartInit` 加参数，
  属于扩张 8.6a 已定的适配器接口。已在 TODOLIST 里记明。

## 自我纠错

- **测试假实现比真代码更容易写错**：第一版"重试耗尽后放弃"用 `failOnceChunk` 写的，而它在重试那次**会成功**，
  于是断言"应当失败"的用例反而走完了上传（`resolved undefined instead of rejecting`）。换成
  `failTransientChunk`（每次都失败）才真的进到耗尽分支。教训：重试用例必须同时断言 `chunk`/`complete`/`abort`
  三个记账数组，否则"重试成功了"和"重试耗尽了"会长得一样。
- 反向确认过一次 abort 边界：`init` 失败那条断言 `abort` 为空数组。

## 决定与理由（跨会话仍然成立的部分）

1. **键名用点分路径，不拿英文原文当键**：`files.noFiles` 而不是 `"No files"`。英文改一个词不该让译文失效，
   而且键名能在代码里 grep 到。
2. **中文表是 `Partial`，未翻的回落英文**，永远不把裸键名漏到界面上。所以一份翻了一半的目录仍可发布——
   这也是后面补三个管理页的前提（不必一次翻完才能合入）。
3. **不做复数引擎**：英文要变名词、中文不变，所以单复数落成两个键（`*One` / `*Other`）+ `tCount`。
   `batch.itemsOne` 与 `batch.itemsOther` 在中文里同形，这是对的——目录一致性测试比的是**占位符集合**而非字面量相等。
4. **不做日期/数字格式化，也不按语言懒加载**：前者是 `Intl` 的事；后者让首屏多一次往返，而我们只有两种语言。
5. **模块级 store + `useSyncExternalStore`，不用 context**：`lib/` 的模块在组件树之外拼文案
   （`mask.ts` / `fileActions.ts` / `transfer.ts` / `batch.ts` / `upload.ts`），把翻译器穿过这些签名要动的地方远多于
   功能本身。代价写在 `locale.ts` 顶部：**`t` 不是响应式的**，渲染文案的组件必须自己订阅（`useT` / `useLocale`）。
6. **两种取用方式，各有理由**：`lib/` 与组件走环境 `t`；`lib/preview.ts` 例外，收**注入**的 `Translate`
   （`previewNotice` / `previewCaption`）——它唯一的调用方直接渲染结果，注入让它保持无全局状态，测试不必摆环境。
   `Translate` 类型声明在 `lib/i18n.ts`，这样 `lib/` 不必反向依赖 `hooks/`。
7. **`summarizeBatch` 去掉了 `noun` / `verb` 参数**：调用方传 `"item"` 就是在传英文语法。两个句子改成围绕
   `{{detail}}` 组织，名词短语由目录拼好再作为参数传入。
8. **`FilesPage` 的错误状态存键、不存字符串**：`load` 是 memo 过的、又坐在 effect 的依赖数组里，若它捕获了
   hook 的翻译器，每次切语言都会重跑 effect、重新拉目录并**丢掉当前选中**。存 `MessageKey` 把翻译挪到渲染期，
   切语言就是免费的。
9. **顺手清掉了英文界面里最后一条硬编码中文**：`crossStorageHint` 原来是
   `` `跨存储复制/移动不支持：${sourceMount} → ${destinationMount}` ``，现在是 `t("transfer.crossStorage", …)`。
10. **`renderToStaticMarkup` 永远渲染 `DEFAULT_LOCALE`**（`useSyncExternalStore` 的 server snapshot），
    所以 `.tsx` 组件测试的英文断言不需要固定语言；只有读环境翻译器的断言（`permissionsFor` / `fileActions`）
    需要 `beforeEach(() => setLocale("en"))`。
11. Node 22 的 `globalThis.navigator.language === "en-US"`，所以 `initialLocale()` 在 vitest 里确定性地解析成 `"en"`。

## 环境备忘（重要，本次踩得最狠的一条）

- **`vitest` / `tsc -p` 看起来"死循环"，其实是沙箱的 broker 在读依赖树。**
  症状：命令长时间无输出、无报错，像挂死。用 `sample <pid>` 抓栈，1727 个采样里约 1715 个停在
  `RequestBrokerSync (in brokered-sandbox-native.node)` → `read`。父进程是 `uv__io_poll` → `kevent`（纯等待），
  worker 持有栈。**代码没有问题。**
- 量级：一个 import `@heroui/react` 的 `.tsx` 套件，vitest 自报
  `Duration 188.73s (transform 1.66s, import 182.61s, tests 22ms)`——**182 秒读模块换 22 毫秒测试**。
  不 import HeroUI 的套件是毫秒级。`tsc -p tsconfig.app.json` 同理（要读整个 HeroUI 的 `.d.ts` 树），本次 294 秒。
- 分界线很干净：`ContextMenu.test.tsx` 及其组件不 import `@heroui/react` → 通过；4 个挂住的套件
  （`preview-views` / `file-views` / `readme-views` / `storage-views`）全都经由组件 import 了它。
  而 pnpm 把每个包都装成软链接，broker 要逐个文件读这棵深树。
- **`dangerouslyDisableSandbox: true` 不解决**（shim 是 Node 层注入的，与 8.5 记的那条一致）。
- **判据**：一个测试文件**在打印任何东西之前**就挂住 → 卡在 import，不是卡在测试
  （vitest 只在文件跑完后才打印该行）。要区分"这个文件卡了"和"整轮慢"，就单独跑它并计时。
- **对策**：给 `vitest` / `tsc -p` 至少 20 分钟上限；或把快的 `.ts` 与慢的 HeroUI `.tsx` 拆成两条命令跑。
  **不要因为"测试挂了"就去改测试——先 sample。** 已写进 `pnpm-in-sandbox` 技能第 8 节。
